Phase 6: Operational hardening and recovery

Outcome

The complete dashboard is safe under concurrency, interruption, stale external state, and sustained local use. Startup performs non-destructive reconciliation; ambiguous worktrees receive explicit repair guidance; multiple browser tabs use a server-authoritative single-writer terminal lease; resource limits, graceful shutdown, privacy, security, accessibility, and load budgets are enforced and verified. The application is operationally ready for packaging, but no release artifact is produced yet.

Purpose

Earlier phases own baseline safety for their features; this phase tests and hardens the interactions among all of them. It closes cross-cutting failure modes—browser ownership races, abrupt shutdown, restored databases, slow clients, path swaps, output floods, stale status, and inaccessible attention UI—without mixing that work with distribution and clean-install concerns.

Dependencies

  • Phases 0–5 acceptance criteria pass, including baseline worktree reconciliation, socket limits, and process cleanup.
  • Foundation per-data-root lock and Phase 3 cross-process Git-common-dir locks are implemented.
  • Threat-model, privacy, accessibility, and fault-injection review checklists are available.
  • Required decision: loopback-only, single-user, daemon-lifetime Pi persistence remains unchanged.
  • Required decision: one browser connection owns PTY input while authenticated observers receive output.

In scope

  • Startup reconciliation and enumerated user repair actions for workspace/worktree/status inconsistencies.
  • Final terminal input lease generation, observer mode, explicit takeover/release, heartbeat expiry, and stale-input rejection.
  • Security review and fixes for binding/authentication, DNS rebinding, CSRF/Origin, filesystem containment, Git refs, process environment/execution, Unix sockets, errors, logs, and dependency boundaries.
  • Concrete resource ceilings and performance budgets for requests, sockets, terminal buffers, clients/runtimes, Git/dialog concurrency, output, and shutdown.
  • Fault injection for database, Git, PTY, status socket, browser, native dialog, disk, and process failures.
  • Accessibility review/fixes for keyboard, focus, status semantics, reduced motion, contrast, errors, and 200% zoom.
  • WAL-safe backup/restore and non-destructive post-restore reconciliation verification.
  • Sanitized diagnostics suitable for troubleshooting without conversation or secret data.

Out of scope

  • Production packaging, desktop entries, release artifacts, checksums, license bundle, clean-install matrix, and release sign-off (Phase 7).
  • tmux or process persistence across daemon restart.
  • Remote access, TLS, accounts, teams, collaboration, telemetry, or cloud services.
  • macOS/Windows commitments, auto-update, sandboxing, or privilege separation.
  • Unmanaged worktree import, merge/rebase/PR UI, file editor, or semantic Pi transcript.

Requirements

  • REQ-06-01: Startup shall reconcile every managed worktree record with canonical filesystem and Git porcelain state before enabling a destructive action on that record.
  • REQ-06-02: Reconciliation shall classify healthy, exact interrupted-success, recoverable missing, mismatch, and ambiguous states without automatically adopting/deleting external files, worktrees, refs, or branches.
  • REQ-06-03: Repair endpoints shall expose enumerated operations only, revalidate current state under the common-dir lock, and refuse any action whose safety precondition changed.
  • REQ-06-04: One authenticated connection shall own input for a runtime; observers shall be visibly read-only and continue receiving output.
  • REQ-06-05: Claim/takeover shall atomically increment a lease generation and notify every client; input must include the generation and stale-generation bytes shall never reach the PTY.
  • REQ-06-06: Disconnect or three missed 5-second heartbeats shall release ownership; an explicit focused observer may claim it.
  • REQ-06-07: Default supported capacity shall be 50 workspaces, 200 managed worktrees, 8 simultaneous Pi runtimes, and 4 terminal clients per runtime; exceeding a limit shall fail before partial allocation.
  • REQ-06-08: Defaults shall bound replay to 1 MiB/runtime (16 MiB hard ceiling), control frames to 64 KiB, input/paste frames to 1 MiB, queued bytes to 4 MiB/client, and API bodies to route-specific limits no greater than 1 MiB.
  • REQ-06-09: Graceful shutdown shall reject new work, notify clients, and stop all Pi groups concurrently within a 10-second global deadline before closing sockets/database and releasing locks/secrets.
  • REQ-06-10: Production logs/diagnostics shall exclude cookies, bootstrap/runtime tokens, provider credentials, terminal bytes, prompts, ask-user answers, system prompts, and raw tool payloads.
  • REQ-06-11: Every executable call shall use argument arrays, explicit cwd/environment, cancellation, timeout, bounded output, and sanitized browser errors; a centralized audit test shall enumerate call sites.
  • REQ-06-12: A complete database backup shall use the SQLite backup API/equivalent WAL-safe mechanism, be integrity-checked, and restore only while the daemon is stopped; restored state is always reconciled with Git.
  • REQ-06-13: Critical non-terminal workflows shall work by keyboard at 200% zoom, and status meaning shall remain available without color or animation.
  • REQ-06-14: The diagnostics API shall return only allowlisted versions, capability states, counts, limits, reconciliation summaries, and sanitized error codes.
  • REQ-06-15: Security review shall have no unresolved high-severity issue before the phase passes.
  • REQ-06-16: Reconciliation of an interrupted branch deletion shall finalize its durable receipt and delete the tombstone only when the stored request matches the recorded final tip/safety target and Git definitively reports the branch absent. Ref-inspection errors shall preserve the in-progress operation and tombstone.

Non-functional requirements

  • Security: Threat-model tests cover malicious origins/DNS rebinding, CSRF, token leakage, symlink/path swaps, ref/argument injection, socket spoofing, stale runtime epochs, oversized traffic, and data-root/common-dir lock bypass.
  • Performance: At supported capacity on the recorded reference Linux machine: cached list APIs p95 ≤200 ms; bridge added echo p95 ≤50 ms; health p95 ≤200 ms during 5 MiB/s output; 200-worktree reconciliation ≤30 seconds; server RSS with 8 fake PTYs ≤ baseline +128 MiB (child RSS excluded); browser JS heap with 8 cached terminals ≤ baseline +160 MiB; after 100 start/stop/mount cycles and forced GC, retained growth ≤ max(10% of post-warmup baseline, 32 MiB).
  • Accessibility: Non-terminal UI follows WCAG-oriented keyboard/focus/name/contrast/error/motion checks. Exact terminal content remains Pi/xterm-controlled but has a named focusable region and non-terminal runtime/status text.
  • Reliability: Recovery is deterministic, mutations are idempotent, shutdown is bounded, no tested dashboard child remains orphaned, and fault injection covers every external-effect boundary.
  • Compatibility: Hardening runs on the reference Linux/browser/Pi matrix chosen from Phase 0 evidence; packaging breadth is deferred.

Technical design

ReconciliationCoordinator runs after migration and before product readiness. It validates locks/permissions, resets stale runtime-dependent states, inspects workspaces, and reconciles managed worktrees and in-progress operation receipts under bounded concurrency and common-dir locks. Deterministic exact postconditions may advance an interrupted lifecycle. Durable branch-delete intent plus definitive ref absence may complete the receipt and delete only the dashboard tombstone metadata; Git inspection errors preserve it. Startup never deletes files or refs.

Each TerminalRuntime owns an input lease {ownerConnectionId, generation, expiresAt}. The first eligible client may claim it. Takeover increments generation under the runtime mutex and broadcasts ownership. Every input frame carries generation; server comparison immediately before pty.write rejects stale buffered input. Output is multicast independently.

Validated configuration centralizes defaults and hard ceilings. Protocol parsers reject sizes early; socket queue bytes are tracked; slow clients are disconnected with replay instructions. Inspection/mutation concurrency, process output, dialog count, request bodies, reconnect rate, and logs are bounded. Diagnostics are built from an explicit privacy allowlist.

Backup uses the SQLite library's online backup facility (or an equivalently safe SQLite operation), verifies integrity/schema, and records no secret. Restore is an offline operator action followed by normal reconciliation.

Data and migrations

This phase may add reconciliation revision/error-code/timestamp fields, never PIDs, terminal bytes, prompts, answers, or secrets. Existing lifecycle/status rows are backfilled deterministically. Migration tests cover every earlier schema and residual WAL state.

Before migration, Phase 1's WAL-safe backup policy remains mandatory. Restore requires a stopped daemon and integrity/schema verification. Because Git is external state, restore always triggers non-destructive reconciliation and cannot automatically recreate/delete worktrees.

Edge cases

  • Two tabs claim simultaneously: runtime mutex produces one generation winner; stale input is rejected.
  • Owner suspends without close: heartbeat expires; resumed buffered input has an old generation.
  • Crash leaves creating/removing records: exact postconditions advance safely; ambiguity remains an error.
  • Crash follows atomic branch deletion but precedes SQLite finalization: matching durable intent plus definitive branch absence completes the receipt and removes the tombstone; inspection failure leaves both intact.
  • Database restore disagrees with Git: repair cards show mismatches without adoption/deletion.
  • Symlink/path changes between checks: postcondition containment/common-dir validation stops mutation.
  • Output flood exceeds queues: slow clients disconnect/replay while PTY and APIs remain responsive.
  • Runtime/client cap reached: request fails before spawning/attaching partial state.
  • Many hung Pi processes at shutdown: concurrent graceful stops escalate and finish by the global deadline.
  • Disk full or database read-only: operation fails visibly, transaction rolls back where possible, and no unsafe retry loops.
  • Diagnostics requested during failures: only allowlisted metadata is returned.
