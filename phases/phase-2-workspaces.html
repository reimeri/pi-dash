Phase 2: Workspace registration

Outcome

A user can click “Add workspace,” choose a directory through a native Linux dialog, register a valid Git repository, and see it immediately in the persistent sidebar. Workspaces survive restarts, can be renamed, expose repository health, and can be removed when they have no managed worktrees. Duplicate aliases, invalid repositories, missing paths, dialog cancellation, and unavailable desktop pickers have clear behavior.

Purpose

Workspaces are the durable roots under which managed worktrees and Pi terminals are organized. This phase establishes safe local directory selection and canonical Git identity before any mutation is allowed. It also delivers the first complete user-facing workflow and validates the SPA/API/database architecture with real filesystem boundaries.

Dependencies

  • Phase 1 application shell, authentication, contracts, database, repositories, and test harness.
  • Git CLI available to the daemon user.
  • Linux graphical session with zenity preferred and kdialog fallback; test adapters do not require a real display.
  • Required technical decision: repository identity is canonical top-level path plus canonical Git common directory.
  • Required technical decision: one native chooser request may be active at a time.

In scope

  • Native Linux directory-dialog adapter, capability probe, cancellation, timeout/abort, and busy handling.
  • Git executable probe and read-only repository inspection service.
  • Canonicalization with realpath, git rev-parse --show-toplevel, --git-common-dir, current branch, and current HEAD.
  • Workspace create, list, detail/health, rename, and empty-workspace removal APIs.
  • Workspace sidebar groups, add/rename/remove dialogs, empty states, loading/error states, and keyboard behavior.
  • Startup/background health refresh for missing or changed repository paths.
  • Typed-path recovery UI only when no native chooser is available; native dialog remains the default.

Out of scope

  • Creating, importing, listing, or deleting Git worktrees.
  • Branch mutation, fetch, clone, commit, merge, rebase, or remote operations.
  • Moving a registered repository or automatically rewriting its stored path.
  • Watching every repository continuously for filesystem changes.
  • Windows/macOS directory dialogs or headless remote operation.
  • PTY or Pi process startup.

Requirements

  • REQ-02-01: The Add Workspace action shall request a native directory dialog from the authenticated daemon.
  • REQ-02-02: The dialog adapter shall prefer zenity, fall back to kdialog, distinguish cancellation from failure, and never invoke a shell.
  • REQ-02-03: The server shall allow at most one active dialog and return DIALOG_BUSY for concurrent requests.
  • REQ-02-04: Registration shall resolve the selected path and Git top-level/common-dir paths canonically before persistence.
  • REQ-02-05: A non-Git directory, inaccessible directory, bare repository without a usable worktree, or invalid Git response shall be rejected with a stable actionable error.
  • REQ-02-06: Registering an already stored canonical repository shall return WORKSPACE_EXISTS and identify the existing workspace.
  • REQ-02-07: Workspace display names shall default from the repository directory, remain user-editable, and produce a stable sanitized slug used for future branch defaults.
  • REQ-02-08: The sidebar shall list workspaces in deterministic user-friendly order and preserve expansion state locally.
  • REQ-02-09: Workspace removal shall be blocked while any related worktree row is active (lifecycle <> 'removed'). Removed branch tombstones do not count as active dependents and are cascade-deleted with workspace metadata; repository worktrees and branches are never deleted by workspace removal.
  • REQ-02-10: Missing/inaccessible repositories shall remain visible as degraded records with repair/remove actions rather than disappearing.
  • REQ-02-11: Repository inspection commands shall use bounded output, timeouts, argument arrays, and explicit cwd.
  • REQ-02-12: Native dialog child processes shall be cancellable when the request or daemon closes.

Non-functional requirements

  • Security: Dialog results are untrusted; canonicalize and validate them. Run zenity/kdialog and Git with shell: false. Do not expose a generic directory-listing or arbitrary executable endpoint.
  • Performance: Listing workspaces reads the database without synchronously running Git for every request. Health probes are cached/bounded and update asynchronously.
  • Accessibility: Add, rename, retry, and remove dialogs are keyboard operable, focus is trapped/restored, errors are associated with fields, and workspace groups use semantic buttons with expanded state.
  • Reliability: Dialog cancellation leaves no row; duplicate requests are idempotent at the canonical-path constraint; missing paths do not crash list rendering.
  • Compatibility: Required on common Linux X11/Wayland sessions through zenity; kdialog supports KDE fallback. Capability failure has a documented typed-path recovery.

Technical design

NativeDirectoryDialog is an injected interface with adapters for zenity and kdialog. At startup, the capability service resolves executables without shell lookup ambiguity and records display/session availability. The route invokes a single-flight dialog coordinator. Zenity receives --file-selection --directory; kdialog receives --getexistingdirectory. Exit code zero with trimmed stdout is a selection, the documented cancel code is cancellation, and all other outcomes become a sanitized unavailable/failure result.

GitInspector executes read-only commands with a fixed environment, timeout, output bound, and -- where applicable. It resolves the selected path, asks Git for the top level, verifies that the top level is a directory worktree, resolves the common Git directory relative to the top level when Git returns a relative path, and captures current branch/HEAD for display only. Database uniqueness on canonical repository path prevents aliases; common-dir information allows later locks to coordinate repositories/worktrees sharing Git metadata.

The frontend uses a workspace store backed by REST query invalidation. Creation is a two-step interaction: native selection, then a confirmation form with resolved path and editable display name. No database row is created before confirmation. The sidebar shows degraded health without removing user context.

interface WorkspaceDto {
  id: string;
  name: string;
  slug: string;
  repositoryPath: string;
  repository: {
    health: "healthy" | "missing" | "inaccessible" | "not_git" | "changed";
    currentBranch: string | null;
    headCommit: string | null;
    checkedAt: string | null;
  };
  worktreeCount: number;
  createdAt: string;
  updatedAt: string;
}

interface NativeDirectoryDialog {
  probe(): Promise<{ available: boolean; adapter?: "zenity" | "kdialog"; reason?: string }>;
  chooseDirectory(options: { signal: AbortSignal }): Promise<{ cancelled: boolean; path?: string }>;
}

Stable workspace errors include DIALOG_BUSY, DIALOG_UNAVAILABLE, PATH_NOT_FOUND, PATH_INACCESSIBLE, NOT_A_GIT_WORKTREE, WORKSPACE_EXISTS, WORKSPACE_HAS_WORKTREES, GIT_UNAVAILABLE, and GIT_TIMEOUT.

Data and migrations

This phase owns migration 0002, which creates the workspace table with canonical repository_path, git_common_dir, display name, stable slug, timestamps, and unique indexes. Health is derived/cached rather than treated as authoritative repository state; optional last-check metadata may be stored if needed for startup UX.

No repository files are migrated or modified. Removing a workspace deletes metadata only. Rollback restores the pre-migration database backup; canonical paths cannot be safely downgraded into guessed aliases.

Edge cases

  • User selects a subdirectory: Git top level is shown and registered, not the subdirectory.
  • User selects an existing linked worktree: it can be a workspace root; common-dir identity is retained for future locking.
  • Path contains spaces, newlines, Unicode, or leading hyphens: argument-array execution and validation preserve valid paths without shell interpretation; display sanitizes control characters.
  • Symlink points to an already registered repository: canonical uniqueness reports the existing workspace.
  • Repository is moved after registration: sidebar marks it missing and offers metadata removal; automatic search is deferred.
  • HEAD is detached or repository is unborn: registration may succeed if it is a usable worktree, but health displays that state and Phase 3 creation may require a valid base commit.
  • Native dialog opens behind the browser: UI shows that a system dialog is active and provides cancellation guidance.
  • Wayland/X11 environment missing: native capability is unavailable and typed-path recovery is presented.
  • Workspace has future managed worktrees: delete returns WORKSPACE_HAS_WORKTREES.

Testing

Unit

  • Dialog exit-code mapping, output trimming, single-flight behavior, adapter selection, timeout, and cancellation.
  • Workspace name/slug normalization, canonical path handling, duplicate detection, and error mapping.
  • Git output parsing for normal, detached, unborn, linked-worktree, malformed, timeout, and inaccessible states.
  • Svelte store updates, dialog focus restoration, field errors, and degraded workspace rendering.

Integration

  • Temporary repositories and symlink aliases register exactly once.
  • Fastify routes enforce authentication, schemas, uniqueness, rename, remove, and request abort cancellation.
  • Deleting/moving a registered fixture produces degraded health without deleting its row.
  • Fake zenity/kdialog executables verify exact argument arrays and no shell usage.

End-to-end

  • Stub native dialog selects a temporary repository; user confirms; workspace appears and survives reload/restart.
  • Cancel creates nothing; invalid selection renders an actionable error; duplicate selection focuses the existing workspace.
  • Rename and remove-empty-workspace workflows are keyboard operable and update the sidebar.
