Phase 7: Packaging and release validation

Outcome

A reproducible Linux MVP artifact can be installed into a clean supported environment, launched through a documented command or optional desktop entry, open an authenticated loopback browser session, locate its packaged Pi extension and native node-pty module, preserve XDG data correctly across upgrade/uninstall, and complete the full real-Pi workflow. Supported versions, dependencies, licenses, backup/recovery, known limitations, and release evidence are published.

Purpose

Operationally hardened source code is not yet a usable release. This phase verifies the distribution boundary: deterministic builds, native dependencies, resource paths, launch/bootstrap UX, Linux desktop integration, clean installation, upgrades, documentation, license obligations, and the final compatibility matrix. It deliberately does not add product capability.

Dependencies

  • Phase 6 hardening, security, fault, accessibility, performance, and recovery gates pass.
  • Supported Node, Git, Pi, Linux distribution/session, browser, zenity/kdialog, and architecture matrix is selected from prior evidence.
  • A clean test environment (container/VM where graphical testing permits) and a reference desktop Linux host.
  • Required decision: first artifact is a documented Linux tarball/npm-style bundle or equivalent that preserves node-pty native compatibility; no auto-update.
  • Required decision: user data is external XDG state and is retained by uninstall unless the user explicitly removes it.

In scope

  • Production builds for Svelte SPA, Fastify server, shared contracts, migrations, and bundled Pi status extension at deterministic paths.
  • Linux launcher that performs capability checks, starts one daemon, obtains the one-time bootstrap URL safely, and uses xdg-open when available.
  • Optional desktop entry/icon that invokes the same launcher and does not create a persistent background service.
  • Artifact layout, checksums, version metadata, source mapping policy, third-party notices, and software bill of materials if selected.
  • Clean install, first launch, upgrade with WAL-safe backup/migration, downgrade refusal, uninstall, and retained-data verification.
  • Supported/unsupported dependency diagnostics for Node ABI, node-pty, Git, Pi, browser, graphical session, and native picker.
  • Full release compatibility matrix and real Pi/ask-user/terminal-extension smoke tests.
  • User guide, installation, configuration, security model, backup/restore, recovery, troubleshooting, known limitations, and release checklist.

Out of scope

  • New application features, protocol changes, or schema changes except release metadata corrections.
  • Deb/RPM/AppImage/Flatpak guarantees unless explicitly chosen after the first artifact passes.
  • Auto-update, package repository hosting, telemetry, crash upload, signing infrastructure beyond available checksum/signature tooling.
  • systemd user service, tmux persistence, always-on daemon, or startup at login.
  • macOS/Windows artifacts or remote deployment.

Requirements

  • REQ-07-01: npm ci from the committed lockfile shall produce the same declared application version and deterministic logical artifact contents; unavoidable native/build timestamps shall be documented.
  • REQ-07-02: The artifact shall contain the built SPA, server, migrations, package metadata, and Pi extension at paths resolved independently of the launcher's current working directory.
  • REQ-07-03: The daemon is the sole owner of the data-root lock and acquires it before migration/readiness. The launcher shall never hold that lock; it starts the daemon or uses the private existing-instance handshake, then waits for capability/readiness before opening the browser.
  • REQ-07-04: The launcher shall transfer the short-lived bootstrap URL without logging it to persistent logs and shall use xdg-open only after readiness; if opening fails it shall print a safe actionable launch instruction.
  • REQ-07-05: A second launcher invocation for the same data root shall focus/open the existing daemon session through a secure existing-instance handshake or fail with clear instructions; it shall never start a competing daemon.
  • REQ-07-06: First launch on a clean supported host shall reach the empty dashboard without manually editing configuration.
  • REQ-07-07: Upgrade shall create and verify the WAL-safe backup before migration, retain workspaces/worktrees/status, reconcile external Git state, and document backup location/restore.
  • REQ-07-08: A binary older than the database schema shall refuse startup without modifying the database.
  • REQ-07-09: Uninstall shall not remove repositories, managed worktrees, Pi sessions/config/credentials, or XDG pi-dash data unless a separate explicit data-removal command is invoked.
  • REQ-07-10: Every distributed dependency license/notice obligation shall be included and the release shall publish checksums; signing is used if project signing infrastructure exists.
  • REQ-07-11: Documentation shall name exact supported/tested versions and distinguish required, optional, degraded, and unsupported capabilities.
  • REQ-07-12: The release test shall execute the complete real-Pi journey including terminal-modifying extensions, ask-user blocked state, done acknowledgement, clean worktree removal, and separate safe branch deletion.
  • REQ-07-13: Release artifacts and production logs shall contain no bootstrap tokens, runtime secrets, provider credentials, terminal output, prompts, or answers.
  • REQ-07-14: Known limitations shall explicitly state local-only access, Linux-first support, daemon-lifetime PTYs, native picker dependencies, exact blocked scope, and non-import of unmanaged worktrees.

Non-functional requirements

  • Security: Artifact provenance/checksum, dependency audit, no embedded secrets, loopback-only launch, safe desktop-entry quoting, secure bootstrap transfer, and no writable executable resource directory.
  • Performance: Installed startup and real workflow remain within Phase 6 budgets; production source maps/assets do not cause excessive startup size or expose server source/secrets.
  • Accessibility: Installation and launch errors are text-readable; desktop entry has a useful name/icon; packaged app passes the Phase 6 keyboard/motion/zoom smoke.
  • Reliability: Clean install, repeated launch, upgrade, interrupted launch, backup/restore, downgrade refusal, and uninstall are repeatable with no repository or user-data loss.
  • Compatibility: Every supported matrix row records distribution, architecture, desktop/session, Node, Git, Pi, browser, picker, install, launch, terminal, ask-user, and upgrade result.

Technical design

The production build emits versioned server ESM, static SPA assets, migrations, and an extension resource into one immutable application tree. Runtime paths derive from import.meta.url or an injected package resource root, never process cwd. node-pty remains a native dependency built/downloaded for the documented Node ABI and architecture; prebuilt strategy is accepted only if its provenance and license are verified.

The launcher is a small argument-array-safe script/program. It validates prerequisites and asks the private existing-instance socket first. If absent, it starts the daemon as foreground child; the daemon alone acquires/holds the data-root lock. The launcher parses narrowly framed readiness containing the ephemeral URL without persistence and invokes xdg-open. It never inherits/transfers a lock descriptor or starts a fallback daemon on another port.

The artifact does not own Pi's ~/.pi/agent data. It passes the packaged status extension via absolute path while preserving all normal user/project Pi resource discovery. XDG dashboard data and central worktrees remain outside the artifact so upgrades replace application files only.

Data and migrations

No product schema change is planned. Release metadata may record application/schema compatibility outside user tables. Upgrade uses the Phase 1/6 WAL-safe backup and forward migrations; clean-install and every supported prior schema fixture are tested. Downgrade opens nothing writable when schema is newer.

Uninstall removes application artifacts only. The user is told the exact XDG data/config/runtime locations and managed-worktree paths; an optional explicit purge procedure requires the daemon stopped and warns that deleting managed worktree directories outside Git commands can leave repository metadata.

Edge cases

  • Launcher cwd is arbitrary or path contains spaces/Unicode: immutable resources still resolve and desktop entry remains safe.
  • Second launch while daemon starts: wait for existing-instance readiness within a bound, then open it or report failure.
  • xdg-open missing/fails: daemon remains available and a clean bootstrap instruction is presented without persistent token logging.
  • Node ABI mismatches node-pty: doctor fails before product readiness with install/rebuild guidance.
  • zenity/kdialog absent: existing dashboard features work and workspace add shows the documented degraded typed-path recovery.
  • Pi absent/unsupported: dashboard can show setup/doctor information but terminal start is disabled clearly.
  • Upgrade backup fails or disk is full: migration does not begin and prior installation/data remain usable.
  • Interrupted artifact replacement: packaging/install procedure is atomic or recovery is documented/tested.
  • Uninstall with live Pi runtimes: launcher stops daemon cleanly or refuses until stopped; repositories/data are retained.
  • Artifact accidentally contains local XDG data or secrets: privacy test fails release.

Testing

Unit

  • Launcher argument/config precedence, readiness framing, exit-code mapping, resource resolution, existing-instance handshake, doctor redaction, and version compatibility.
  • Artifact manifest/license/checksum generation and forbidden-file/content scanning.

Integration

  • Build from clean lockfile twice and compare manifest hashes excluding documented nondeterministic native metadata.
  • Install/launch from arbitrary cwd/path, missing prerequisites, occupied port, existing daemon, browser-open failure, and native-module mismatch.
  • Upgrade with active/residual WAL, backup/integrity check, migration, restore/reconcile, newer-schema refusal, and retained worktrees.
  • Uninstall preserves XDG data, central worktrees, Git repositories, and all Pi configuration/sessions.

End-to-end

  • Clean supported Linux host completes bootstrap → native workspace selection → exact-base worktree create → real Pi terminal → ask-user blocked → done/acknowledge → clean removal → separate branch delete.
  • Optional desktop entry launches/focuses the same daemon and passes keyboard/reduced-motion/zoom smoke.
  • Each compatibility-matrix row records pass/fail evidence and no unsupported row is advertised as supported.

  • ☐ Artifact/log/privacy scans contain no forbidden secret, terminal, prompt, or user-data content.

  • ☐ User installation, security, backup, recovery, troubleshooting, and data-retention documentation is verified by a clean tester.
