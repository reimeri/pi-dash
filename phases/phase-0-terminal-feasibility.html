Outcome

An executable Linux spike proves that a Svelte 5 page using @battlefieldduck/xterm-svelte can drive an ordinary interactive Pi process through node-pty and a WebSocket without losing Pi's terminal UI. The spike demonstrates resizing, essential key chords, paste, ask-user custom UI, worktree-specific cwd, disconnect/reconnect, process exit, and a non-invasive lifecycle status side channel. A written decision record captures measured behavior and any design changes required before product construction.

Purpose

The exact terminal is the defining integration, and it carries the project's highest technical risk. Browser keyboard reporting, alternate-screen redraws, PTY lifecycle, xterm resource cleanup, and extension side-channel behavior must be observed against real Pi rather than assumed. This phase is intentionally a bounded throwaway harness: it retires architectural uncertainty before database, workspace, and production API work makes a terminal redesign expensive.

Requirements

  • REQ-00-01: The harness shall spawn pi directly with shell: false, the selected worktree as cwd, and a bundled spike status extension.
  • REQ-00-02: Pi's startup header, transcript, tools, editor, footer, selectors, and custom extension UI shall render legibly in xterm.
  • REQ-00-03: Browser terminal input shall reach the PTY once and only once; no duplicated characters are permitted.
  • REQ-00-04: Positive xterm column/row changes shall resize the PTY and trigger a correct Pi redraw.
  • REQ-00-05: Shift+Enter shall insert a newline and Alt+Enter shall use Pi's follow-up behavior, using explicit escape translation if required.
  • REQ-00-06: Escape and Ctrl+C shall retain Pi's abort/clear semantics and shall not be captured by the web page.
  • REQ-00-07: The ask-user extension's terminal-native selector and free-text input shall be operable from the browser.
  • REQ-00-08: The status extension shall report lifecycle events over a private Unix socket without writing visible terminal text or delaying Pi.
  • REQ-00-09: A disconnected browser shall not terminate the PTY; reconnect shall produce an intelligible current screen through replay plus redraw.
  • REQ-00-10: Closing the harness shall terminate Pi gracefully and leave no child process or socket behind.
  • REQ-00-11: The decision record shall state pass/fail results, package versions, observed caveats, and whether the production architecture can proceed unchanged.

Non-functional requirements

  • Security: Bind the spike to loopback; do not expose arbitrary command input; use random status runtime IDs/tokens; do not log terminal content by default.
  • Performance: The dashboard bridge shall add no more than 50 ms p95 input-to-echo latency on localhost with the fake PTY; reconnect shall become usable within 2 seconds when replay is available; a 5 MiB/s, 30-second output test shall not freeze the page; 100 mount/unmount cycles shall leave no live sockets/observers and less than 10% retained-heap growth after forced GC in the test harness.
  • Accessibility: The terminal host shall have an accessible label, visible focus treatment outside xterm, and a documented keyboard-only path to focus the terminal.
  • Reliability: Disconnects, malformed WebSocket messages, status-socket absence, Pi exit, and repeated browser refreshes shall not crash the daemon.
  • Compatibility: Record Linux distribution, desktop/session type, browser, Node, Pi, xterm-svelte, xterm, and node-pty versions. Chromium is the required spike browser; Firefox is a useful secondary check.

Technical design

The spike consists of a tiny Svelte client and Fastify server under spikes/terminal-bridge. The server accepts a worktree path through a startup option, validates it as a Git top level, creates a Unix socket under a temporary private directory, then starts one PTY. The PTY executable is the resolved Pi binary and receives PI_DASH_STATUS_SOCKET, PI_DASH_RUNTIME_ID, and PI_DASH_STATUS_TOKEN.

The Svelte component binds the xterm instance exposed by xterm-svelte, dynamically loads FitAddon and Unicode11Addon, observes its host, and forwards onData. It handles onBinary separately so binary mouse reports are not corrupted. The wrapper registers stable callbacks and performs explicit disposal in Svelte teardown because xterm-svelte's component lifecycle must not be assumed to dispose the terminal and event resources.

The server keeps a sequence-numbered ring buffer with a deliberately small configurable cap so overflow behavior can be exercised. Reconnect sends the available replay and then performs a resize nudge to request a complete Pi redraw. The experiment records whether this is sufficient for the alternate screen. If not, the decision record compares xterm serialization/headless state or a later tmux capture strategy; Phase 4 may not begin until one bounded approach is selected.

The status extension starts its socket client only on session_start and listens for the pi-dash:attention shared event. The compatible ask-user fixture emits start immediately before awaiting UI and end in finally; tool preflight alone must never mark blocked. Connection errors are swallowed/debug-logged outside the terminal, and ANSI output is never parsed for state.

Interfaces and contracts

type ClientFrame =
  | { v: 0; type: "input"; data: string }
  | { v: 0; type: "binaryInput"; dataBase64: string }
  | { v: 0; type: "resize"; cols: number; rows: number }
  | { v: 0; type: "replayFrom"; seq: number };

type ServerFrame =
  | { v: 0; type: "hello"; runtimeId: string; earliestSeq: number; latestSeq: number }
  | { v: 0; type: "output"; seq: number; data: string }
  | { v: 0; type: "runtime"; state: "running" | "exited"; exitCode: number | null }
  | { v: 0; type: "status"; event: string }
  | { v: 0; type: "error"; code: string; message: string };

The spike protocol is version zero and disposable. Frame sizes, resize bounds, and UTF-8 behavior are explicit. The status socket uses LF-delimited JSON and rejects events with a wrong runtime ID/token. A development-only GET /spike/diagnostics may expose counts and versions, but not terminal bytes or secrets.

Data and migrations

No production schema or migration is introduced. The spike may write temporary socket and diagnostic files beneath a mkdtemp directory and must delete them on clean shutdown. It shall not read or mutate the future application database. Any captured measurements must omit terminal content and secrets.

Edge cases

  • Pi executable missing or non-executable: startup fails before listening with an actionable diagnostic.
  • Selected path is not a Git worktree: PTY is not started.
  • Status extension cannot connect: Pi remains fully usable and status capability is shown as degraded.
  • Browser closes while ask-user is open: Pi remains blocked; reconnect permits answering in the terminal.
  • Output buffer wraps while disconnected: server sends a reset marker and forces redraw rather than pretending replay is complete.
  • Zero-sized or hidden terminal host: do not send a zero resize; fit when visible again.
  • WebGL unavailable: use xterm's default renderer; WebGL is not required.
  • IME or Unicode wide characters: verify cursor alignment with Unicode11Addon and record limitations.
  • Pi exits itself through /quit: PTY exit is reported and the WebSocket remains able to display final state.
  • Daemon receives SIGINT/SIGTERM: one graceful cleanup path runs at most once.
