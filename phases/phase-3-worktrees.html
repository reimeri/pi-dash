Phase 3: Managed worktrees

Outcome

Users can create a named Git worktree beneath a registered workspace, using a new branch named pi-dash/<slug> from the workspace repository's current HEAD or another selected valid ref. Managed worktrees appear under their workspace, persist across restarts, and can be safely removed with dirty-tree protection and optional separate safe branch deletion. The removed tombstone remains only while branch cleanup is pending; successful cleanup removes the UI/database record and permits slug reuse. Interrupted and externally changed worktrees are detected and represented explicitly.

Purpose

Managed worktrees provide isolated filesystem and branch contexts for independent Pi agents. This phase implements the project's primary Git mutation boundary before PTYs are introduced, allowing worktree invariants, failure recovery, and destructive safeguards to be tested without process-lifecycle complexity.

Dependencies

  • Phase 2 canonical healthy workspace records and Git inspection/process utilities.
  • Central application data directory with user-only permissions.
  • Git version supporting git worktree add/remove/list --porcelain.
  • Required technical decision: in-process and cross-process mutation locks are keyed by canonical Git common directory so related records or separate data roots cannot race.
  • Required technical decision: MVP worktree creation always creates a new branch; existing-branch and detached modes are deferred.
  • Required technical decision: branch deletion proves mergedness, then uses atomic expected-OID git update-ref -d; force branch deletion is not included.

In scope

  • Central managed path allocation using stable workspace/worktree IDs and a readable slug suffix.
  • Current HEAD/base-ref discovery and bounded branch/ref listing for creation UI.
  • New branch and worktree creation with lifecycle records and compensation after failure.
  • Per-common-dir mutation locking within the daemon.
  • Managed worktree listing, branch/base metadata, filesystem/Git health, and sidebar entries.
  • Dirty state check including untracked files.
  • Structured removal inspection, safe clean removal, a separately typed destructive override within the deterministic allocation boundary, durable quarantine recovery, and separate safe branch deletion.
  • Startup/manual reconciliation against git worktree list --porcelain.
  • Repair/retry messaging for interrupted creating, removing, and error records.

Out of scope

  • Pi process or PTY startup, terminal controls, and status tracking.
  • Import/adoption of worktrees not created by the dashboard.
  • Creating worktrees from existing branches, sparse checkout, or automatic submodule initialization.
  • Fetch, remote branch discovery, clone, merge, rebase, push, pull request, or branch force deletion.
  • Automatic stashing or repair of externally changed Git metadata; destructive removal always requires explicit typed confirmation.
  • Moving a managed worktree to another location.

Requirements

  • REQ-03-01: The creation form shall snapshot the workspace's current HEAD (or selected ref) to an exact object ID and receive a short-lived signed token binding workspace ID, ref, commit, and expiry. Creation shall require the token plus matching baseRef/baseCommit and use that exact commit even if the ref moves.
  • REQ-03-02: The default branch shall be pi-dash/<worktree-slug> and shall pass git check-ref-format --branch.
  • REQ-03-03: The target path shall be allocated beneath <data>/worktrees/<workspace-id>, contain the worktree ID, and be rejected if canonical containment cannot be established.
  • REQ-03-04: Creation shall execute git worktree add -b <branch> <path> <base> with argument arrays, explicit repository cwd, timeout, and bounded output.
  • REQ-03-05: Mutating operations sharing a Git common directory shall be serialized through both daemon-local and OS-visible cross-process locks and return a busy/conflict response rather than overlap.
  • REQ-03-06: A durable creating record shall exist before Git mutation and transition to ready only after postcondition verification.
  • REQ-03-07: Failed creation shall not silently delete an ambiguous external path; compensation is allowed only for the exact app-allocated path and branch known to have been created by the failed operation.
  • REQ-03-08: Removal preparation shall return a signed, expiring snapshot with exact expected/current path and Git identity, dirty counts, lock reason, mounts, strategy, and branch disposition. Normal removal shall remain available only for an exact clean unlocked worktree.
  • REQ-03-09: Dirty, locked, branch-changed, detached, or Git-unprovable removal shall require a second destructive review and the exact typed confirmation delete. Mounted content and a recorded path outside the deterministic allocation shall never be overrideable.
  • REQ-03-10: Branch deletion shall be a separate post-removal endpoint and confirmation. Under the common-dir lock it shall verify no worktree uses the branch, prove the recorded tip is merged into the explicit safety target, and atomically execute git update-ref -d <ref> <expected-tip>; moved/unmerged refusal shall not undo removal. After definitive branch absence, one SQLite transaction shall complete the operation receipt and delete the tombstone.
  • REQ-03-11: Removing a workspace with any active managed worktree record shall remain forbidden. Removed tombstones shall not count as active dependents and shall be deleted if workspace metadata is removed.
  • REQ-03-12: Reconciliation shall never adopt or delete an unrecorded worktree automatically.
  • REQ-03-13: Worktree names and branch components shall reject control characters, path separators where inappropriate, empty slugs, reserved Git forms, and collisions.
  • REQ-03-14: Every create/remove/delete-branch mutation shall require a client operation ID (idempotency key); retries with the same request hash shall return the durable prior/in-progress result, while reuse with different input shall be rejected. Operation receipts shall retain the historical worktree ID without a cascading worktree foreign key so remove/delete retries survive tombstone deletion.
  • REQ-03-15: Removal shall revalidate the signed inspection under the shared lifecycle and common-directory locks after stopping Pi. State changes invalidate confirmation and require a fresh review.
  • REQ-03-16: Proven Git worktrees shall use normal, single-force, or double-force Git removal according to the confirmed state. Unprovable Git identity shall use identity-checked quarantine removal only at the deterministic allocation and shall leave unknown Git metadata untouched.
  • REQ-03-17: A durable removal journal shall permit crash recovery without touching a replacement at the original path. A removed row exists only while branch cleanup remains; otherwise the row is forgotten and a replayable receipt retains manual-cleanup warnings.

Non-functional requirements

  • Security: All destinations remain under the app-owned root; no user-supplied command strings; symlink/path-swap checks occur before and after mutation; browser errors redact unnecessary command output.
  • Performance: Worktree listing is database-first with bounded health refresh. Ref listing is capped and filterable. Git mutations run asynchronously without blocking the Node event loop.
  • Accessibility: Creation/removal confirmations expose branch, base, path, dirty warning, and consequences in text; progress is announced; destructive actions require unambiguous labels and focus restoration.
  • Reliability: Lifecycle markers, per-common-dir locks, postcondition verification, idempotent reconciliation, and conservative compensation protect against crashes and external Git changes.
  • Compatibility: Linux filesystem and Git CLI; paths with spaces/Unicode supported; case sensitivity follows the underlying filesystem and Git ref rules.

Technical design

WorktreeService owns invariants and calls an injected GitWorktreeManager. When the form opens, the server resolves the ref to baseCommit and signs a short-lived snapshot token binding workspace/ref/commit. Creation verifies that token without re-resolving moved HEAD. The service acquires a daemon mutex plus advisory OS lock under the canonical per-UID Linux namespace /run/user/<uid>/pi-dash-git-locks (secure /tmp/pi-dash-<uid> fallback), independent of configurable XDG/data roots. A DB transaction inserts lifecycle/idempotency records; external Git runs outside long DB transactions.

Because filesystem/Git mutation cannot share SQLite atomicity, the lifecycle is a saga with conservative compensation. The record stores operation metadata such as expected branch, target path, and base commit. After a failed add, the service re-inspects git worktree list --porcelain, target existence, and branch existence before deciding whether a safe cleanup is possible. Ambiguous cases remain error for user repair.

Removal preparation produces a signed structured identity snapshot. Exact clean unlocked worktrees use safe removal; mismatches, dirt, and locks require a second review plus typed delete, while mounts and non-deterministic paths remain blocked. After lifecycle claim and runtime stop, the snapshot is revalidated under the Git lock. Proven worktrees use Git normal/single-force/double-force removal. An eligible observed refs/heads/pi-dash/* branch may be adopted while the previous ref remains untouched. Unprovable Git identity uses deterministic quarantine removal and leaves Git metadata manual. A durable phase journal supports restart recovery and either retains a branch tombstone or atomically forgets the row with replayable warnings.

Data and migrations

This phase owns migrations for the worktree table and durable mutation-operation ledger: UUID, workspace foreign key, name/slug, canonical managed path, branch/base refs, exact base commit, final branch tip, lifecycle, sanitized last-error code/message, request hash/result, and timestamps. The operation ledger retains a historical worktree ID without cascading ownership of the worktree row, while workspace deletion still removes its receipts. Unique constraints cover live managed paths, workspace slugs, branch identity where representable, and idempotency keys.

The schema-v5 migration converts legacy completed/in-progress branch-deletion markers into matched durable receipts, removes completed tombstones and obsolete branch-deleted/safety-target columns, and aborts rather than attributing an unmatched operation. Rollback restores the database only and cannot undo Git worktrees or branches already changed, so downgrade documentation requires reconciling/removing managed worktrees with the newer version before restoring a backup.

Edge cases

  • Workspace HEAD changes while form is open: server validates the unexpired signed workspace/ref/commit snapshot and uses its token-bound commit without requiring the ref still point there.
  • Unborn HEAD: default creation is disabled until a valid base commit is selected/created externally.
  • Branch/path appears after validation but before add: Git failure is reconciled and returned as collision or create failure.
  • Two workspace records share common Git metadata: common-dir lock serializes mutations.
  • Process crashes after Git add but before DB ready update: startup reconciliation verifies branch/path/common-dir and promotes the record if exact.
  • Directory exists but Git identity is unprovable: only the exact deterministic allocation can be quarantined after typed confirmation; Git metadata remains untouched.
  • Dirty worktree contains only untracked files: normal removal is blocked, while forced removal clearly reports and discards them after typed confirmation.
  • Worktree lock exists: show its reason and require typed confirmation before Git double-force removal.
  • Branch was changed externally: show expected/current refs; adopt only an unclaimed refs/heads/pi-dash/* observed branch and leave the prior ref untouched.
  • Safe branch deletion refuses an unmerged or moved branch: the tombstone stays removed and offers manual follow-up.
  • Daemon stops after durable delete intent: definitive branch absence completes the receipt and deletes the tombstone; an inspection error leaves both intact for later reconciliation.
  • Successful branch cleanup releases the old slug and branch reservation, allowing a new managed worktree to reuse them.
  • Submodules exist: Git may create directory entries, but automatic submodule init/update is deferred and not implied.

Testing

Unit

  • Name/slug/ref validation, branch derivation, containment, collision, and path allocation.
  • Porcelain parsers for worktree list/status, including spaces, detached entries, pruning markers, and malformed output.
  • Lifecycle reducer/saga decisions and conservative compensation matrix.
  • Removal UX state and branch-warning presentation.

Integration

  • Create from HEAD and named base in temporary repositories; verify exact branch, path, common dir, and database record.
  • Concurrent creation under shared common dir serializes; duplicate branch/path returns stable errors.
  • Concurrent terminal-start/removal simulation proves ready → removing CAS prevents any new runtime after removal eligibility is claimed and verifies ready/error/removed rollback outcomes.
  • Removal inspection reports tracked/untracked dirt, changed/detached branches, locks, common-dir mismatches, and mounts; signed confirmation is revalidated before safe or forced mutation.
  • Force tests cover Git single/double force, branch adoption, symlink quarantine, filesystem-only forgetting, stale tokens, and crash recovery; branch deletion remains separately mergedness checked.
  • Fault injection before/after Git mutation validates startup reconciliation, definitive absence checks, operation replay after row deletion, and inspection-error preservation.
  • Remove, delete the merged branch, recreate the same slug, and verify the branch/path database reservations were released.
  • External move/remove/branch change updates health without destructive auto-repair.

End-to-end

  • Create a worktree from a registered fixture, observe nested sidebar entry, restart daemon, and observe persistence.
  • Dirty or switch the worktree branch, review expected/current identity, type delete, force-remove it, acknowledge untouched refs, then separately delete the adopted merged branch.
  • Simulate branch-not-merged refusal and verify successful worktree removal plus actionable warning.

Acceptance criteria

  • ☐ A user can create a new managed branch/worktree from current HEAD or a selected valid base.
  • ☐ Path, branch, and database postconditions are verified before ready state.
  • ☐ Related Git mutations are serialized and recover from injected interruption without unsafe cleanup.
  • ☐ Dirty tracked or untracked changes block normal removal.
  • ☐ No forced dirty removal is exposed; post-removal branch deletion is a separate mergedness-checked atomic expected-OID operation that stores a replayable receipt and deletes the tombstone.
  • ☐ Successful branch cleanup removes the UI entry and permits reuse of the former slug/branch identity.
  • ☐ Unknown/external worktrees are never adopted or deleted automatically.
  • ☐ Tests pass.
  • ☐ Build, lint, and type checking pass.
  • ☐ Documentation is updated.
