Phase 5: Workflow status tracking

Outcome

Every managed worktree displays a reliable workflow attention indicator: gray idle, animated blue working, pulsing amber blocked while a compatible ask-user extension actually awaits terminal UI, and green done after Pi fully settles. State comes from a bundled fail-open Pi extension over a private authenticated Unix socket, not from terminal-output parsing. Done remains visible until the user views/focuses or explicitly acknowledges that worktree.

Purpose

Multiple independent Pi terminals are useful only if users can see which agent needs attention without opening each one. Pi exposes exact lifecycle and tool events to extensions, allowing a minimal side channel to report state while preserving the interactive TUI. This phase defines deterministic transitions, ordering, persistence, acknowledgement, and degraded behavior.

Dependencies

  • Phase 4 runtime UUID/secret allocation, bundled extension launch path, terminal focus/selection events, and authenticated browser connections.
  • Pi lifecycle events session_start, session_shutdown, agent_start, and agent_settled, plus Pi's shared extension event bus.
  • A compatible ask-user extension emits the documented pi-dash:attention start immediately before awaiting terminal UI and end in finally; tool preflight events are not treated as waiting.
  • Unix-domain sockets under the private XDG runtime directory.
  • Required technical decision: blocked detection is exact only for cooperating interactive extensions, initially the reference ask-user integration; silence, tool preflight, and prompt wording are never interpreted as blocked.

In scope

  • Bundled Pi extension with lifecycle subscriptions, Unix socket client, framing, authentication fields, sequence numbers, reconnect, and idempotent cleanup.
  • Daemon StatusSocketServer, event validation, runtime authentication, stale-event rejection, and state reducer.
  • Workflow status persistence with revision, reason, timestamps, and acknowledgement.
  • Status updates delivered to the SPA through a dashboard events WebSocket or equivalent authenticated real-time channel.
  • Sidebar status icons, labels/tooltips, animations respecting reduced motion, workspace aggregate attention, and status detail text.
  • Done acknowledgement from selection, terminal focus/click, terminal input, or explicit action.
  • Exact ask-user wait start/end correlation by interaction ID, including answer, cancel, abort, and thrown errors.
  • A documented shared-event protocol and reference ask-user compatibility fixture/patch for extension authors.
  • Degraded status-channel health separate from runtime and workflow state.

Out of scope

  • Heuristic detection from quiet periods, ANSI output, prompt wording, or model text ending in a question.
  • Automatic support for every third-party blocking tool or arbitrary extension dialog.
  • Native desktop notifications, sounds, email, mobile push, or system tray.
  • Detailed task progress, percent complete, tool log, token/cost display, or semantic transcript.
  • Cross-daemon persistent active processes or remote event delivery.
  • Bundling or silently replacing a user's ask-user extension; incompatible versions remain working-state rather than being guessed blocked.

Requirements

  • REQ-05-01: The status extension shall begin connection work only from session_start or a relevant event, not from its factory, and close resources idempotently on session_shutdown.
  • REQ-05-02: Status transport failure shall never block, delay materially, abort, or alter Pi, tool execution, ask-user UI, or session lifecycle.
  • REQ-05-03: Side-channel frames shall contain only lifecycle metadata; prompt text, answers, message content, tool arguments/results, system prompts, and credentials are forbidden.
  • REQ-05-04: The daemon shall authenticate each frame with the currently active runtime ID and per-runtime secret and reject events from exited/replaced runtimes.
  • REQ-05-05: agent_start shall transition the current runtime's workflow state to working.
  • REQ-05-06: A validated pi-dash:attention start emitted immediately before an extension awaits user UI shall add its interaction ID to the active blocking set and transition to blocked.
  • REQ-05-07: The cooperating extension shall emit matching end in finally; it removes only its own ID. State remains blocked while any interaction is active and returns to working when the set is empty.
  • REQ-05-08: agent_settled shall always transition to done, even when the worktree terminal is already selected.
  • REQ-05-09: Selecting, focusing/clicking, typing in, or explicitly acknowledging a worktree after its current done revision shall transition it to idle.
  • REQ-05-10: Acknowledgement shall include or compare the status revision so a late acknowledgement cannot clear a newer done event.
  • REQ-05-11: Every extension load shall create an extensionInstanceId epoch. An authenticated session_start handshake atomically establishes the current epoch; sequence ordering is scoped to (runtimeId, extensionInstanceId), and prior-epoch frames are rejected.
  • REQ-05-12: Workflow state and runtime state shall remain separate; stopped/crashed is not encoded as blocked or done.
  • REQ-05-13: On daemon restart, stale working/blocked states shall be reset to idle because no runtime survives; unacknowledged done may remain visible.
  • REQ-05-14: Sidebar icons shall include text accessible to assistive technology and not rely on color or motion alone.
  • REQ-05-15: The shared-event reason allowlist shall initially accept only ask_user; unsupported tools/dialogs do not become blocked heuristically.
  • REQ-05-16: Application-event subscribers shall receive an atomic initial status/runtime snapshot with a server cursor before incremental events; reconnect by cursor shall replay or explicitly require a fresh snapshot so REST/WebSocket races cannot lose state.

Non-functional requirements

  • Security: Socket directory is mode 0700, socket access is user-scoped, secrets are random and never logged, frames are size-limited/validated, runtime authentication uses constant-time comparison where appropriate.
  • Performance: Lifecycle reporting is non-blocking and low volume; status fan-out coalesces redundant updates; sidebar transitions render without rerendering terminal output.
  • Accessibility: Every icon has a textual state, animation respects prefers-reduced-motion, focus acknowledgement is predictable, and workspace aggregate indicators have labels.
  • Reliability: Duplicate/reordered events, extension reload, socket restart, daemon shutdown, Pi crash, ask-user cancellation, and missing ask-user extension have deterministic outcomes.
  • Compatibility: Supports the documented Pi event API/version range on Linux. If unsupported, terminal remains usable and UI reports status integration unavailable.

Technical design

The Fastify daemon starts one StatusSocketServer. TerminalManager supplies each Pi runtime a UUID/secret. The packaged extension writes bounded LF-delimited JSON and tracks agentActive plus the complete active blocking-interaction set. After reconnect it sends one atomic snapshot at a sequence boundary before incrementals; it may drop superseded event frames only because the snapshot restores full state.

Each extension load creates a random epoch and listens to pi.events.on("pi-dash:attention", ...). A compatible ask-user emits start immediately before its await ui... and end in finally. Starts/ends update a set by interaction ID, so overlap is correct. Pi's tool_execution_start remains preflight and never directly marks blocked. Event handlers enqueue non-blocking writes; socket errors never reach the TUI.

The daemon validates protocol, frame length, runtime/worktree pair, secret, extension epoch, sequence, timestamp sanity, and event-specific fields. An authenticated session-start frame atomically replaces the current extension epoch and clears prior-epoch transient correlations. A pure reducer produces a new status revision using daemon receipt time as authoritative changedAt; extension time is diagnostic only. Durable status is updated transactionally, then appended to a bounded server event stream. Runtime exit invokes a server-authoritative reducer event even if extension shutdown was not delivered.

Done acknowledgement uses compare-and-set semantics: acknowledge revision N only if current state is done and current revision equals N (or is the exact revision sent to the client). Opening/focusing a terminal sends acknowledgement after the UI has actually selected/focused it. If it was already focused when done arrives, done remains until a subsequent click/focus/input or explicit acknowledgement, matching the chosen semantics.

Data and migrations

A migration finalizes workflow_status as one row per worktree with checked state, reason, monotonically increasing revision, changed timestamp, acknowledged timestamp, and optional non-secret integration diagnostics. A worktree creation inserts idle revision zero in the same transaction as its durable record. Worktree deletion cascades status deletion.

On upgrade, missing rows are backfilled as idle. On daemon startup, working/blocked rows become idle with reason runtime_reset and a new revision because runtimes are not persistent. Done rows remain done so unread completion is not silently lost. Rollback treats unknown status values conservatively as idle after restoring the prior database backup.

Edge cases

  • Ask-user extension not installed/active: no blocked event occurs; agent lifecycle still reports working/done.
  • Ask-user is answered, cancelled, aborted, or throws: its finally emits matching blocking_wait_end; agent_settled later marks done.
  • Pi/extension reload replaces extension instance: authenticated session-start installs a new epoch; its sequence restarts safely and all prior-epoch frames/correlations are rejected.
  • Status socket starts late/restarts while interactions overlap: extension reconnects and atomically snapshots agentActive plus the complete interaction set before new events.
  • Duplicate/out-of-order frames within an epoch are ignored; old-epoch frames are rejected; metrics/debug log the condition without changing state.
  • Two blocking calls overlap: ending one keeps blocked until the active blocking-call set is empty.
  • Old runtime emits after restart: runtime ID/secret mismatch rejects it.
  • User acknowledges revision 17 as revision 18 becomes done: compare-and-set returns conflict and preserves done.
  • Terminal is selected when settled: done remains until a later focus/click/input or explicit acknowledgement.
  • Pi crashes while blocked: runtime exit clears stale blocked to idle while runtime badge shows crashed.
  • Multiple worktrees update rapidly: per-worktree revisions and aggregate recalculation remain deterministic.
  • Reduced motion requested: working/blocked icons become static shapes with text while retaining color distinctions.

Testing

Unit

  • Complete reducer transition table, active blocking-call sets, epoch handshakes, per-epoch sequence/revision checks, acknowledgement compare-and-set, startup reset, and aggregates.
  • Event/snapshot schemas, atomic snapshot reducer, size/auth/privacy, LF chunk splitting, partial/multiple frames, reconnect during overlap, and dropped-event recovery.
  • Svelte status store ordering, icon labels, reduced motion, workspace aggregate, and acknowledgement triggers.

Integration

  • Fake extension authenticates and drives idle → working → blocked → working → done → idle, overlapping blocking calls, and sequence restart under a new extension epoch.
  • Wrong token/runtime, stale seq, duplicate event, malformed frame, socket disconnect, and old runtime are rejected safely.
  • Fake Pi runtime exit and daemon restart reset active states but preserve done.
  • Real Pi with compatible ask-user validates that blocked begins only when UI wait opens and ends through answer, cancel, abort, and thrown-error cleanup.

End-to-end

  • Two worktrees show independent animated working and blocked/done states while terminals switch.
  • Done remains after settlement and clears only on post-settlement view/focus/input/acknowledge.
  • Refresh/reconnect receives an atomic cursor snapshot, then ordered incremental updates or an explicit resync; status channel degradation leaves terminal functional.
  • Screen-reader-visible labels and reduced-motion mode are asserted.

Acceptance criteria

  • ☐ Sidebar reliably displays idle, working, ask-user blocked, and unacknowledged done states.
  • ☐ With a compatible ask-user extension, blocked lasts exactly from immediately before awaiting its UI until matching finally cleanup; preflight-only/blocked tool calls never report blocked.
  • ☐ Done always occurs on agent_settled and revision-safe acknowledgement changes it to idle.
  • ☐ Status failures never alter or prevent Pi terminal interaction.
  • ☐ Side-channel frames contain no conversation/tool payload content or credentials.
  • ☐ Stale and old-runtime events cannot regress current state.
  • ☐ Indicators are accessible without color or motion alone.
  • ☐ Tests pass.
  • ☐ Build, lint, and type checking pass.
  • ☐ Documentation is updated.
