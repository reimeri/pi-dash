Outcome

A production-shaped local application starts through one npm command: a loopback Fastify daemon migrates a SQLite database, serves an authenticated Svelte 5 SPA in production, exposes health/version information, and supports shared validated contracts and structured errors. The UI displays its two-pane dashboard shell, connection state, empty workspace sidebar, and setup guidance. Unit, integration, and browser test infrastructure is operational.

Purpose

All later phases need a stable security boundary, data directory policy, schema/migration mechanism, API conventions, frontend state pattern, logging policy, and automated test harness. Establishing these once prevents Git, PTY, and status features from inventing incompatible contracts or bypassing local authentication.

Requirements

  • REQ-01-01: The repository shall use npm workspaces with reproducible lockfile installs and common build, test, lint, format, and type-check scripts.
  • REQ-01-02: The daemon shall bind to 127.0.0.1 by default and reject a configured non-loopback host.
  • REQ-01-03: Startup shall resolve XDG paths, create private data/runtime directories, open SQLite, and apply pending migrations before reporting ready.
  • REQ-01-04: The daemon shall generate a high-entropy, short-lived, one-use bootstrap token, exchange it for an HttpOnly SameSite=Strict cookie, and avoid logging either secret. The bootstrap response shall use Cache-Control: no-store, Referrer-Policy: no-referrer, contain no third-party resources, redirect to a clean URL, and ensure failed exchanges do not retain the token in application-controlled browser history.
  • REQ-01-05: All protected REST endpoints and future WebSocket upgrades shall share one authentication and Origin/Host policy.
  • REQ-01-06: GET /api/v1/health shall report application version, readiness, schema version, and capability placeholders without exposing paths or secrets unnecessarily.
  • REQ-01-07: API errors shall follow the master-plan error envelope with stable codes and request IDs.
  • REQ-01-08: Runtime request/response schemas shall be defined once in packages/contracts and used for server validation and frontend typing.
  • REQ-01-09: The SPA shall show disconnected, connecting, ready, migration-failed, and unauthorized startup states.
  • REQ-01-10: Graceful shutdown shall stop accepting requests, close WebSockets, flush logs, close SQLite, and remove runtime secrets/socket placeholders idempotently.
  • REQ-01-11: Configuration shall support CLI/environment overrides for port, data/config/runtime directories, Pi executable placeholder, and log level while preserving loopback-only policy.
  • REQ-01-12: Startup shall acquire an exclusive advisory lock for the canonical data root before backup/migration; a second daemon shall fail clearly, while stale lock metadata shall be recovered only after proving no owner holds the OS lock.
  • REQ-01-13: Every upgrade migration shall first create a consistent SQLite backup through the SQLite backup API or equivalent WAL-safe mechanism and verify that it can be opened.

Non-functional requirements

  • Security: Runtime and token files are mode 0600; directories are mode 0700; cookies are HttpOnly and SameSite=Strict; state-changing requests enforce same-origin and content type; logs redact tokens/cookies.
  • Performance: Warm daemon startup excluding migrations should target under one second on a typical development machine; the empty SPA should become interactive promptly and avoid large terminal dependencies until Phase 4 routes load them.
  • Accessibility: Use semantic landmarks, a skip link, keyboard-visible focus, live regions for connection/errors, and sufficient contrast in the base shell.
  • Reliability: Migrations are transactional; startup failure is explicit; shutdown is idempotent; filesystem and database errors include actionable diagnostics without partial readiness.
  • Compatibility: Linux and current supported Node LTS/current range; Chromium for required E2E; no dependence on a specific desktop environment yet.

Technical design

The root npm workspace contains apps/web, apps/server, packages/contracts, and packages/pi-extension. The extension package is a placeholder in this phase so build and resource-path strategy can be fixed before Phase 5. The server uses a composition root that constructs config, logger, paths, database, auth, and Fastify plugins; tests can inject temporary directories, an in-memory or temporary-file database, clocks, random-token functions, and fake capability probes.

Fastify owns all production HTTP and static files. During development, Vite serves the SPA and proxies /api and future upgrade paths to Fastify. The browser never reads a bootstrap token from persistent JavaScript storage. The launch command prints or opens a short-lived one-time bootstrap URL; the no-store/no-referrer endpoint contains no third-party resources, validates and consumes the token, sets the cookie, and redirects with history replacement to a clean URL. Sessions are invalidated when the daemon restarts.

Drizzle defines only foundation-owned metadata and the migration journal; workspace, worktree, operation, and workflow-status tables are introduced by their owning phases. Database access occurs through repository interfaces rather than directly in routes. SQLite uses foreign keys, WAL mode where supported, a busy timeout, explicit transactions, and a WAL-safe backup API before upgrades. Migration failure prevents readiness and does not serve the application as if healthy.

The SPA uses a small typed API client and centralized connection/error state. It renders a fixed-width/resizable-ready sidebar region and flexible main region but does not implement resizing yet. CSS variables establish status colors while respecting reduced motion in later animated components.

Data and migrations

Migration 0001 creates only foundation-owned metadata required to identify schema/application versions; feature tables arrive in later owning phases. A migration journal records applied versions and checksums. Startup applies forward-only migrations transactionally; tests prove a fresh database and the previous fixture version both reach the same schema.

Rollback is backup-and-restore through a consistent SQLite backup created with the backup API (or equivalent mechanism that includes WAL state), never a live file copy and never an automatic downgrade. The backup is opened and integrity-checked before migration proceeds. The app reports a newer-than-supported schema as an explicit incompatibility.

Edge cases

  • XDG_RUNTIME_DIR missing: create a private runtime directory under the data root and warn at debug level.
  • Port occupied: exit with a clear message and no partial ready state.
  • Bootstrap token replay: reject after first successful exchange.
  • Browser visits / without a session: show/redirect to launch guidance without leaking token details.
  • Wrong Host or Origin, including DNS rebinding attempts: reject before route/upgrade handling.
  • Database locked or read-only: fail readiness with request ID and underlying path redacted from normal browser errors.
  • Migration interrupted: SQLite transaction rolls back; next startup retries safely.
  • Static assets missing in production: health can report degraded startup, but protected product UI is not falsely reported ready.
  • Duplicate shutdown signals: cleanup executes once.
