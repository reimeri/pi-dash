Phase 4: Interactive Pi terminal runtime

Outcome

Selecting a ready worktree lazily starts one interactive Pi process in that worktree and shows its exact terminal UI in the main Svelte panel. Users can type, paste, resize, use Pi shortcuts and extension UI, switch among worktrees without stopping processes, reconnect after a browser refresh, and explicitly stop or restart a runtime. Runtime state and crashes are visible independently from later workflow status dots.

Purpose

This phase delivers the core product experience using the production architecture validated in Phase 0. It turns managed worktrees into live Pi environments while preserving Pi's terminal extensibility, isolates process ownership in the daemon, and creates stable terminal contracts for status integration and hardening.

Dependencies

  • Phase 0 terminal decision record and its selected alternate-screen reconnect mechanism.
  • Phase 1 authenticated REST/WebSocket infrastructure and shared contracts.
  • Phase 3 ready/healthy managed worktrees and terminal-stop removal hook.
  • node-pty, @battlefieldduck/xterm-svelte, xterm FitAddon and Unicode11Addon.
  • A discoverable supported pi executable; user's Pi settings/credentials/extensions remain external.
  • Required technical decision: one runtime per worktree and process persistence only for the daemon lifetime.

In scope

  • Pi executable/version probe and configurable executable path.
  • In-memory TerminalManager with one PTY runtime per managed worktree.
  • Lazy idempotent start on first worktree selection; explicit stop and restart.
  • Authenticated versioned terminal WebSocket with input, binary input, output sequencing, resize, replay/reset, runtime state, ping/heartbeat, and errors.
  • Bounded per-runtime output buffers and outbound backpressure policy.
  • xterm-svelte terminal panel with explicit lifecycle cleanup, FitAddon, Unicode11Addon, responsive layout, focus, paste, modified-key handling, and error overlays.
  • Switching among multiple live worktrees without stopping hidden runtimes.
  • Browser refresh/reconnect while daemon and Pi continue running.
  • Graceful process-tree stop on API request, worktree removal, and daemon shutdown.
  • Runtime state: stopped, starting, running, stopping, and crashed.

Out of scope

  • Workflow idle/working/blocked/done lifecycle and Pi status extension logic (Phase 5).
  • Survival across daemon restart, tmux, systemd-managed child sessions, or terminal history persistence.
  • Remote access, SSH runtimes, containers, sandboxing, or arbitrary shell terminals.
  • Multiple concurrent input writers with final lease/takeover UX (basic single owner only; hardening in Phase 6).
  • Semantic rendering of Pi messages or RPC/SDK control panels.
  • Image-protocol guarantees beyond behavior naturally supported by xterm/browser and validated examples.

Requirements

  • REQ-04-01: Selecting a worktree shall acquire the shared lifecycle coordinator, atomically verify lifecycle is still ready, and register the starting/current runtime before releasing it. Lifecycle removing, removed, or error rejects start.
  • REQ-04-02: TerminalManager shall enforce at most one live dashboard PTY per worktree under concurrent requests.
  • REQ-04-03: The PTY shall spawn the Pi executable directly with the worktree path as cwd, shell: false semantics, the documented sanitized inherited environment, and dashboard extension path placeholder.
  • REQ-04-04: User/global and trusted project Pi resources shall load normally; the dashboard shall not override Pi's agent directory, session directory, theme, tools, or approvals by default.
  • REQ-04-05: The terminal WebSocket shall authenticate before attachment and validate protocol version, frame schema, frame size, dimensions, and runtime/worktree association.
  • REQ-04-06: Each output chunk shall have a monotonically increasing sequence and be retained only within configured byte/chunk limits.
  • REQ-04-07: Disconnecting the last browser shall not stop Pi; reattachment shall follow the Phase 0 replay/redraw contract.
  • REQ-04-08: Hidden/zero-size terminal panels shall not resize PTYs to invalid dimensions; visibility restoration shall refit.
  • REQ-04-09: Input from xterm onData shall be forwarded once; binary reports use a binary-safe frame; output uses terminal.write without newline transformation.
  • REQ-04-10: Required Pi keys and ask-user terminal UI shall behave as recorded in Phase 0.
  • REQ-04-11: On Linux the PTY child shall be verified by integration test as the owned session/process-group leader. Stop shall signal that group through the live PTY identity, wait a bounded interval, and escalate, while guarding against signaling after handle exit/PID reuse.
  • REQ-04-12: Pi exit code/signal and sanitized startup failures shall update runtime state and remain visible until restart.
  • REQ-04-13: Worktree removal shall await runtime stop before invoking Git removal.
  • REQ-04-14: Terminal/addon/observer/socket resources shall be disposed on client eviction and daemon runtime disposal.
  • REQ-04-15: Start is resource-idempotent by worktree and always returns the sole current runtime; stop is idempotent and returns stopped when already stopped. Restart alone requires an idempotency key so retries return the original operation/runtime and changed-input key reuse fails.
  • REQ-04-16: Pi shall inherit user runtime variables needed for normal behavior (HOME, PATH, SHELL, locale, XDG, SSH agent, provider credentials, and Pi configuration), while all internal PI_DASH_* authentication/bootstrap variables are removed and only the three per-runtime status variables are reintroduced.

Non-functional requirements

  • Security: No generic spawn endpoint; executable and extension paths come from trusted config/package resources; WebSockets enforce cookie, Host, Origin, worktree authorization, message limits, and input ownership.
  • Performance: The production bridge shall meet the Phase 0 p95 50 ms localhost input-to-echo target, reconnect to a usable screen within 2 seconds when replay is available, keep health API p95 below 200 ms during the 5 MiB/s output fixture, and bound each runtime replay buffer to the configured default 1 MiB/hard ceiling. Terminal dependencies are lazy-loaded.
  • Accessibility: Terminal region has an accessible name containing workspace/worktree, visible focus boundary, keyboard focus command, runtime/error text outside color-only indicators, and reduced-motion-compatible controls.
  • Reliability: Concurrent starts collapse to one operation; all exits clean handles; disconnects do not affect PTY; stop/restart are idempotent; daemon shutdown drains runtimes.
  • Compatibility: Linux and browsers accepted by Phase 0. Exact package versions are pinned. Default renderer works without WebGL.

Technical design

TerminalManager is a composition-root service. Its per-worktree mutex collapses concurrent starts and serializes lifecycle operations; an in-memory idempotency map covers daemon-lifetime retries. Start enters Phase 3's shared WorktreeLifecycleCoordinator, verifies ready, and registers starting before release, so a concurrent removal cannot pass ready → removing unnoticed. It then resolves Pi/extension, sanitizes inherited environment, allocates runtime identity, and creates the PTY. If spawn fails, runtime registration rolls back while durable worktree lifecycle remains ready.

Each runtime owns PTY listeners, output sequence, bounded ring buffer, connection registry, basic single input owner, dimensions, timestamps, and shutdown controller. On Linux, the node-pty child/session ownership assumption is verified with a child/grandchild fixture; group signaling uses the still-live runtime handle/PID only until its exit callback wins, preventing post-exit PID reuse. The PTY data callback appends once and broadcasts with backpressure handling. Slow clients are disconnected or required to replay. PTY exit transitions state and finalizes listeners after delivering exit state.

The Svelte app renders a terminal workspace area. Recently used terminals may remain mounted in a bounded LRU cache to preserve browser state when switching; eviction calls explicit terminal/addon/observer/socket disposal. If the selected worktree has no cached terminal, it starts/attaches and applies replay. Fit happens after fonts and container dimensions are ready and whenever the main panel changes.

The status extension passed on the Pi command line can initially be a no-op transport package until Phase 5. Its argument must already be present so Phase 5 does not alter the process launch contract. Pi project trust remains an interactive terminal concern, preserving exact behavior.

Data and migrations

No durable runtime/process table is introduced because PIDs and sockets become stale across daemon restarts. Worktree DTOs may expose runtime state joined from TerminalManager. If operational crash metadata is desired, store only bounded last-exit diagnostics on the worktree or a separate audit table; it must not be interpreted as a reconnectable process.

Daemon restart always reconstructs TerminalManager empty and reports all runtimes stopped. Existing Pi session JSONL remains owned by Pi in its normal storage and is not migrated or copied.

Edge cases

  • Two clients select a stopped ready worktree simultaneously: exactly one PTY starts and both attach; if removal has claimed removing, both receive WORKTREE_NOT_READY.
  • Worktree disappears between selection and spawn: start fails without launching Pi.
  • Pi prompts for project trust or login: exact interactive prompt remains usable in terminal; dashboard does not bypass it.
  • Pi executable changes or is upgraded while server runs: existing runtimes continue; new start re-probes according to cache policy.
  • Browser refresh after ring-buffer overflow: reset/redraw contract restores usability or shows a clear reconnect limitation established by Phase 0.
  • Terminal hidden by sidebar/navigation: no zero resize; refit when visible.
  • Very fast output or slow observer client: bounded queue disconnects/replays the client while PTY remains alive.
  • /quit cleanly exits Pi: runtime becomes stopped (clean exit) and offers Start; unexpected nonzero exit becomes crashed.
  • Stop during ask-user or tool execution: Pi receives graceful signal/abort opportunity, then escalation.
  • Restart requested while stop is in progress: serialized operation returns the final new runtime, not two processes.
  • Native node-pty build unavailable: startup capability reports PTY unavailable with installation guidance.

  • Frontend socket reducer, replay/reset, reconnect backoff, cache eviction cleanup, key translation, and focus state.

Integration

  • Fake Pi validates exact cwd, args, environment allow/deny behavior, input/output, resize, exit codes, session/process-group identity, SIGTERM-ignoring grandchildren, escalation, and PID-reuse guard.
  • Concurrent start/stop/restart and worktree removal use the shared lifecycle coordinator: removal CAS before start rejects launch; start registration before removal is stopped before Git; no process can start after removing.
  • Authenticated WebSocket rejects wrong Origin/session/version and handles malformed/oversized frames without daemon failure.
  • Disconnect/reconnect, replay, overflow reset, slow client, and multiple observer behavior.
  • Guarded real Pi smoke repeats Phase 0 terminal and extension UI checks in production components.

End-to-end

  • Create/select worktree, observe lazy fake-Pi start and exact terminal interaction, switch away/back, resize, refresh, and reconnect.
  • Start two worktrees and verify independent terminals/cwds/process controls.
  • Stop/restart/crash display correct runtime state; worktree removal waits for stop.
  • Repeated navigation/mount/eviction has stable browser/server resource counts.
