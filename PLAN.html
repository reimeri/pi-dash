Planning baseline

Pi Dashboard Implementation Plan

A Linux-first, local-only web dashboard that creates managed Git worktrees and gives every worktree an exact interactive Pi terminal. The browser is the presentation layer; a loopback-only Node.js daemon owns filesystem access, Git operations, PTYs, process lifecycle, and status aggregation.

Goals and boundaries

Product goals

  • Register local Git repositories as workspaces.
  • Create dashboard-managed Git worktrees in a central application data directory.
  • Run one ordinary interactive Pi process per active worktree, with the worktree as Pi's current working directory.
  • Render Pi's complete terminal UI, including extension-provided custom components and dialogs.
  • Keep worktree terminals running when the user switches between sidebar entries or temporarily disconnects the browser.
  • Show useful idle, working, blocked, and done attention states without parsing human-readable terminal output.
  • Make destructive Git and filesystem actions explicit, validated, and recoverable.

Initial boundaries

  • Linux is the supported target. macOS is a likely follow-up after platform validation.
  • The daemon binds to loopback only. Remote access and multi-user authorization are excluded.
  • Pi processes do not survive a dashboard daemon restart. tmux or another supervisor is deferred.
  • The dashboard does not recreate Pi as a native web chat interface and does not concurrently open a Pi session through RPC or SDK.
  • The dashboard manages only worktrees recorded in its own database. Importing arbitrary existing worktrees is deferred.
  • Merge, rebase, pull-request, code-editor, and diff-review workflows are deferred.

Confirmed decisions

Application

Svelte 5 single-page application built with Vite, served by a dedicated Fastify Node.js daemon.

Terminal

@battlefieldduck/xterm-svelte over a custom WebSocket protocol to a node-pty process running interactive Pi.

Persistence

SQLite with Drizzle schema and migrations. npm workspaces, Vitest, and Playwright form the project toolchain.

Pi startup

Start Pi lazily on the first selection of a worktree terminal, then keep it alive until stop, removal, or daemon shutdown.

Git defaults

New branch from the workspace repository's current HEAD; branch name pi-dash/<slug>; worktree path under the central app data directory.

Removal

Block dirty worktree removal. After removal, optionally perform a separately confirmed mergedness check and atomic expected-OID ref deletion; successful branch cleanup stores an idempotent receipt, deletes the worktree tombstone, and releases its slug for reuse.

Status

ask_user tool execution means blocked. agent_settled means done until the terminal is viewed or acknowledged.

Folder selection

Use a native Linux directory dialog initiated by the daemon, with explicit cancellation and unavailability handling.

Frontend

The Svelte SPA owns navigation, dialogs, terminal presentation, focus acknowledgement, status icons, and reconnect behavior. It never receives unrestricted filesystem or command-execution capabilities. @battlefieldduck/xterm-svelte wraps xterm.js; the app loads the Fit and Unicode 11 addons, uses a ResizeObserver, and explicitly disposes terminal/addon resources. The transport remains custom rather than using xterm's AttachAddon because resize, replay, process state, input ownership, and protocol versioning require control messages.

Daemon

The daemon is the only privileged application component. It serves production static assets, provides versioned REST endpoints, upgrades terminal and status WebSockets, launches native dialogs, validates paths, serializes Git mutations by canonical Git common directory, and owns all PTYs. Development runs Vite separately with API/WebSocket proxying; production is one loopback process.

Pi integration

Each runtime launches the user's configured pi binary in interactive mode with the managed worktree as cwd. The dashboard adds one bundled extension through --extension. It does not disable or replace the user's global or project extensions, prompts, skills, themes, settings, credentials, trust behavior, or sessions.

pi --extension /absolute/path/to/pi-dash-status-extension.ts

The status extension uses Pi lifecycle events and a private Unix-domain socket. Its failure must never block Pi startup or tool execution. It opens resources on session_start, closes them idempotently on session_shutdown, and reconnects after Pi reload/new/resume/fork lifecycle replacement.

Process and runtime ownership

  • There is at most one dashboard-owned Pi PTY per worktree.
  • A worktree runtime can exist with zero attached browsers.
  • The server keeps a bounded sequence-numbered output buffer for browser reconnects.
  • Daemon shutdown sends a graceful termination signal, waits for Pi cleanup, then escalates if necessary.
  • Runtime process state is independent from workflow attention state.

Workspace and worktree lifecycle

Workspace registration

  1. The user opens the native directory dialog.
  2. The daemon launches zenity --file-selection --directory, with kdialog --getexistingdirectory as a fallback adapter.
  3. The chosen path is resolved with realpath and validated using git rev-parse --show-toplevel and git rev-parse --git-common-dir.
  4. The canonical repository root and common Git directory are stored. Duplicate canonical repositories return a conflict rather than creating aliases.

Only one native chooser is active at a time. Cancellation is a successful no-selection result; missing display variables or picker executables produce an actionable unavailable error. A typed-path fallback may be offered for headless recovery but is not the primary UX.

Worktree creation

  1. Validate the requested display name, slug, base ref, derived branch name, and managed target path.
  2. Resolve the workspace's current HEAD to an exact commit when the dialog opens and issue a short-lived signed snapshot token binding workspace, ref, and object ID. Creation sends the token plus baseCommit; baseRef remains display/audit metadata.
  3. Acquire the in-process and cross-process locks keyed by canonical Git common directory.
  4. Insert a creating record and run git worktree add -b pi-dash/<worktree-slug> <path> <base-commit> using an argument array and no shell.
  5. Verify the resulting top level, branch, and common Git directory, then mark the record ready.
  6. On failure, remove any safe partial target, preserve a diagnostic, and expose an explicit retry/repair path.

Worktree removal

  1. Check git status --porcelain=v1 --untracked-files=all before disturbing a running Pi terminal; reject all dirty worktrees with no force path.
  2. Under the shared worktree lifecycle coordinator, atomically transition ready → removing; terminal start uses the same coordinator and is rejected after this point.
  3. Stop and dispose the Pi runtime only after the preliminary check and lifecycle claim say removal is eligible.
  4. Recheck dirtiness immediately after shutdown to close the race, then run normal git worktree remove without --force. New dirt or exact intact failure restores ready; ambiguity becomes error.
  5. After verifying Git no longer reports the worktree, transition it to removed and retain a temporary tombstone containing the verified branch and final tip so branch cleanup can be a separate operation.
  6. If separately confirmed afterward, verify no worktree uses the branch and that the recorded tip is merged into the chosen safety target, then atomically delete the ref with git update-ref -d <ref> <expected-tip>. A moved/unmerged branch refusal does not invalidate worktree removal.
  7. After definitively proving the branch is absent, use one SQLite transaction to complete the durable idempotency receipt and delete the tombstone. The card/sidebar entry disappears and the former slug/branch identity becomes reusable.
  8. If interruption occurs after durable delete intent, reconciliation finalizes only when Git definitively reports the branch absent; inspection errors retain the operation and tombstone for a later retry.

Terminal lifecycle

Launch

Selecting a ready worktree calls the idempotent start endpoint and opens its terminal socket. The terminal manager chooses a configured Pi executable, verifies it, creates a PTY with a known UTF-8 environment and default dimensions, and supplies private status-channel environment variables. It does not invoke an intermediate shell.

Transport

Protocol v1 uses JSON WebSocket envelopes for control and UTF-8 terminal data. Every output event has a monotonically increasing sequence. On attach, the server sends a hello message, process state, buffer range, and replay or reset instruction. Resize values are bounded before calling pty.resize(cols, rows).

The frontend forwards xterm onData exactly once, forwards onBinary with binary-safe encoding when needed, and sends resize only after the FitAddon computes positive dimensions. Shift+Enter and Alt+Enter are explicitly tested and, if xterm/browser defaults are insufficient, translated to the escape sequences Pi documents for modified Enter keys.

Switching and reconnect

  • Switching worktrees detaches presentation, not the PTY.
  • A bounded client cache may retain recently viewed xterm instances; evicted instances are explicitly disposed.
  • The daemon keeps a bounded output ring buffer. Buffer overflow advances the earliest sequence and tells stale clients to reset.
  • Full-screen terminal replay is validated in Phase 0. Resize-triggered redraw is the primary recovery mechanism; a server-side terminal snapshot is deferred unless the spike proves replay inadequate.
  • Only one browser connection owns input for a runtime. Additional connections are read-only until they explicitly take over; full lease behavior is hardened in the final phase.

Workflow status model

StateSourceMeaningSuggested UI
idleStartup or completion acknowledgementPi is ready and no completed result currently requires attention.Static gray dot
workingagent_start; end of a blocking interactionPi is processing, retrying, compacting, or continuing queued work.Animated blue spinner
blockedCooperating ask-user extension emits dashboard blocking_wait_start immediately before awaiting its terminal UIA supported interactive extension is actually waiting for user input.Pulsing amber icon
doneagent_settledThe complete run settled and has not yet been viewed or acknowledged.Static green dot

A compatible ask-user extension emits a shared Pi event immediately before awaiting its dialog and a matching end event in finally. Each start adds its interaction ID to an active blocking set and each end removes only that ID. State returns to working only when the set is empty; agent_settled clears transient correlations and moves it to done. Pi tool preflight events alone never claim that UI is waiting.

agent_settled always records done, even if that worktree is currently selected. A subsequent selection, terminal focus/click, terminal input, or explicit acknowledgement marks it idle. State changes carry revisions so late socket events cannot overwrite newer transitions.

Blocked detection is deliberately exact rather than heuristic. A quiet model request is still working. Other user-input tools can be added later through a configurable allowlist or a shared Pi extension event contract.

  "event": "agent_start | agent_settled | blocking_wait_start | blocking_wait_end | session_start | session_shutdown",
  "interactionId": "optional", "reason": "ask_user when blocking" }

// Snapshot frame at a sequence boundary after connect/reconnect
{ "v": 1, "kind": "snapshot", "runtimeId": "uuid", "worktreeId": "uuid",
  "token": "per-runtime secret", "extensionInstanceId": "random load epoch", "seq": 8,
  "agentActive": true,
  "blockingInteractions": [{ "id": "...", "reason": "ask_user" }],
  "timestamp": "ISO-8601" }

Messages are LF-delimited JSON with strict size limits. An authenticated session_start establishes the extension-instance epoch; sequence ordering is scoped to that epoch and older epochs are rejected. Reconnect sends an atomic extension snapshot containing agent activity and the complete active blocking-interaction set before incremental events. The daemon uses receipt time for state ordering. The extension sends no prompt, message content, tool arguments, tool output, credentials, or system prompt data.

The browser's application-events WebSocket starts with an atomic status/runtime snapshot and server cursor, then ordered incremental events. If the cursor expires, the server explicitly requires a fresh snapshot so reconnect cannot lose a transition.

Security and reliability

  • Bind only to IPv4 and/or IPv6 loopback; startup rejects non-loopback binding in the initial product.
  • Create a per-launch bootstrap token in a user-only runtime file, exchange it for an HttpOnly, SameSite=Strict cookie, then remove the token from the URL.
  • Validate HTTP Host and WebSocket Origin and require authentication for every non-health API and upgrade.
  • Canonicalize paths with realpath; verify managed worktree destinations remain beneath the application-owned root.
  • Run Git and Pi with executable plus argument arrays and shell: false.
  • Validate IDs, names, branch components, refs, terminal dimensions, WebSocket message sizes, and status frames at trust boundaries.
  • Acquire an exclusive per-data-root daemon lock before migration/readiness, and serialize mutating Git operations with both in-process and cross-process locks keyed by canonical Git common directory.
  • Use database lifecycle markers for interrupted create/remove operations and a detached idempotency ledger for branch deletion; reconcile against definitive Git worktree/ref inspection on startup.
  • Bound terminal buffers, socket queues, logs, request bodies, and native dialog concurrency.
  • Never log authentication tokens, Pi credentials, terminal input/output, prompt content, or status side-channel secrets by default.
  • Use SIGTERM followed by a bounded wait and SIGKILL escalation for process-tree cleanup.

Implementation phases

  1. Phase 0: Terminal and Pi feasibility — retire PTY, xterm-svelte, keyboard, extension UI, replay, and status-channel risks with an executable spike.
  2. Phase 1: Application foundation — establish the workspace repository, loopback daemon, authenticated SPA shell, shared contracts, database, migrations, and test harness.
  3. Phase 2: Workspace registration — native Linux directory selection, Git repository validation, and workspace CRUD in the sidebar.
  4. Phase 3: Managed worktrees — safe branch/worktree creation, listing, reconciliation, dirty protection, removal, and optional safe branch deletion.
  5. Phase 4: Interactive Pi terminal runtime — lazy Pi startup, PTY/WebSocket transport, xterm terminal, switching, resizing, reconnect, and process controls.
  6. Phase 5: Workflow status tracking — Pi lifecycle side channel and exact idle/working/blocked/done sidebar behavior.
  7. Phase 6: Operational hardening and recovery — reconciliation, single-writer input leases, security review, concrete resource budgets, accessibility, and fault tolerance.
  8. Phase 7: Packaging and release validation — reproducible Linux artifacts, clean installation, compatibility matrix, documentation, and full release-gate verification.

Each phase has an observable product increment, explicit exclusions, contracts, tests, acceptance criteria, and verification commands. A phase is complete only when its acceptance criteria and automated checks pass; later-phase features must not be silently pulled into earlier scope.

Risks and open follow-ups

RiskMitigation or decision point
xterm/browser keyboard reporting differs from a native terminal.Phase 0 tests Pi shortcuts and custom translation for modified Enter before product architecture proceeds.
Replaying bytes does not reconstruct Pi's alternate-screen state.Test bounded replay plus forced resize. If inadequate, evaluate xterm serialization/headless snapshots before Phase 4 acceptance.
xterm-svelte lifecycle does not automatically dispose every terminal/listener.Wrap it in an application component with explicit observer, addon, socket, and terminal disposal; include repeated mount/unmount leak tests.
Native dialog commands vary across Linux desktops.Use an adapter with zenity primary, kdialog fallback, capability reporting, cancellation semantics, and a documented typed-path recovery.
User Pi versions or extensions differ.Probe pi --version, document the supported range, make status integration fail-open, and test with representative terminal extensions and ask-user.
Two browser tabs send conflicting input.Single-writer lease with visible takeover, read-only observers, heartbeat expiry, and integration tests.
Interrupted Git operations leave DB/filesystem disagreement.Lifecycle markers, per-common-dir locks, startup reconciliation, repair actions, and no silent destructive cleanup.
Central worktree directory fills disk.Report creation failures clearly, avoid hidden copies, expose paths and sizes later, and keep cleanup explicit.

Deferred product questions

  • Whether macOS becomes an officially supported target and which native picker adapter it uses.
  • Whether Pi runtimes should survive daemon restarts through tmux.
  • Whether additional blocking tools use a configuration allowlist or emit a shared extension event.
  • Whether existing worktrees can be imported and adopted safely.
  • Whether a later semantic UI uses Pi RPC/SDK alongside, but never concurrently writing, an interactive session.
Planning rule: the interactive terminal is the product's primary Pi interface. Structured integration exists to manage lifecycle and attention state, not to replace or constrain Pi's extensible terminal UI.
